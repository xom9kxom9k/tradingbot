## 1. Цели и границы проекта

### 1.1 Бизнес-цель заказчика

Получить систему, которая:

1. По заранее определённой торговой стратегии **сообщает, когда входить в сделку** — в лонг или в шорт;
2. Имеет **воспроизводимые бэктесты** этой стратегии на исторических данных;
3. Позволяет заказчику **просматривать прошлые результаты на удобных интерактивных графиках**;
4. **Отправляет сообщение о сделке в Telegram-бота** в момент появления сигнала.

### 1.2 Что входит в объём работ (In scope)

| # | Компонент | Описание |
|---|---|---|
| 1 | Загрузчик данных | Скачивание и кэширование исторических и live OHLCV-свечей с биржи |
| 2 | Библиотека индикаторов | EMA, ATR, ADX, Donchian, RSI, объёмные фильтры |
| 3 | Стратегия | Реализация стратегии из раздела 7 через общий интерфейс `Strategy` |
| 4 | Бэктест-движок | Событийный бэктестер с комиссиями, проскальзыванием, защитой от look-ahead |
| 5 | Метрики и аналитика | Полный набор метрик доходности/риска, журнал сделок |
| 6 | Walk-forward и оптимизация | Подбор параметров + out-of-sample валидация + Monte Carlo |
| 7 | Визуализация | Интерактивный Streamlit-дашборд + экспорт статичного HTML-отчёта |
| 8 | Live/paper движок | Реальное отслеживание рынка и генерация сигналов на закрытии свечи |
| 9 | Telegram-бот | Уведомления о сигналах + команды управления и просмотра |
| 10 | Инфраструктура | Конфиги, логирование, БД состояния, Docker, CI, тесты, документация |

### 1.3 Что НЕ входит в объём работ (Out of scope)

- **Автоматическое выставление ордеров на биржу.** Бот только сигнализирует («говорит, когда входить»). Модуль исполнения проектируется как интерфейс-заглушка (`BrokerAdapter`) с реализацией `PaperBroker`, но реальный `LiveBroker` в этой версии не пишется.
- Хранение и использование приватных API-ключей биржи с правами на торговлю.
- Мультиаккаунтность, веб-авторизация, платёжные подписки.
- Мобильное приложение.
- HFT/тиковые стратегии, арбитраж, маркет-мейкинг.

### 1.4 Дисклеймер (обязателен в README)

Проект является исследовательским инструментом. Сигналы не являются индивидуальной инвестиционной рекомендацией. Результаты бэктестов не гарантируют будущей доходности.

## 2. Глоссарий

| Термин | Значение |
|---|---|
| **OHLCV** | Свеча: Open, High, Low, Close, Volume |
| **Bar close** | Момент закрытия свечи; единственный момент, когда стратегия принимает решения |
| **Look-ahead bias** | Ошибка, при которой стратегия использует данные из будущего |
| **Signal** | Объект-намерение: направление, цена входа, стоп, тейки, размер позиции, причина |
| **Trade** | Закрытая сделка: вход, выход, PnL, R-мультипликатор |
| **R** | Единица риска = \|цена входа − цена стопа\|. PnL измеряется в R |
| **Equity curve** | Кривая капитала счёта во времени |
| **MaxDD** | Максимальная просадка капитала от локального максимума |
| **Walk-forward (WFA)** | Валидация: оптимизация на in-sample окне, проверка на следующем out-of-sample окне |
| **IS / OOS** | In-sample (обучающая выборка) / Out-of-sample (проверочная выборка) |
| **Slippage** | Проскальзывание — разница между ожидаемой и фактической ценой исполнения |
| **Funding** | Ставка финансирования на бессрочных фьючерсах |

## 3. Функциональные требования

### FR-1. Данные

- **FR-1.1** Система загружает исторические OHLCV с биржи Binance USDT-M Futures через `ccxt` (публичные эндпоинты, ключи не требуются).
- **FR-1.2** Поддерживаемые таймфреймы: `15m`, `1h`, `4h`, `1d`. Базовый (по умолчанию) — `4h`.
- **FR-1.3** Поддерживаемые символы (по умолчанию): `BTC/USDT`, `ETH/USDT`, `SOL/USDT`, `BNB/USDT`, `XRP/USDT`. Список расширяется через конфиг.
- **FR-1.4** Глубина истории: минимум с `2019-01-01` (или с момента листинга инструмента) по текущий момент.
- **FR-1.5** Данные кэшируются локально в Parquet. Повторный запуск догружает только недостающий хвост (инкрементальная догрузка).
- **FR-1.6** Валидация данных: отсутствие дубликатов по timestamp, монотонность времени, отсутствие пропусков баров (пропуски логируются и заполняются флагом `is_gap`), отсутствие `NaN` в OHLCV, проверка `low <= open,close <= high`.
- **FR-1.7** Все временные метки — UTC, tz-aware. Timestamp свечи = время её **открытия**.

### FR-2. Стратегия

- **FR-2.1** Стратегия реализует абстрактный интерфейс `Strategy` (раздел 6.3), что позволяет добавлять новые стратегии без изменений в движке.
- **FR-2.2** Стратегия работает в обе стороны: **long и short**.
- **FR-2.3** Все параметры стратегии задаются через конфиг (YAML), никаких «магических чисел» в коде.
- **FR-2.4** Стратегия принимает решение **только по закрытым свечам**. Использование `close` текущей формирующейся свечи запрещено.
- **FR-2.5** Точная логика — раздел 7.

### FR-3. Бэктест

- **FR-3.1** Событийный (bar-by-bar) бэктест-движок.
- **FR-3.2** Учёт: комиссии (taker/maker), проскальзывания, funding-ставки (упрощённая модель — фиксированная ставка за 8 часов удержания), минимального шага цены и лота.
- **FR-3.3** Порядок обработки бара строго определён (раздел 8.2), чтобы исключить look-ahead.
- **FR-3.4** Поддержка портфельного режима: несколько символов одновременно с общим капиталом и лимитом на число одновременных позиций.
- **FR-3.5** Результат бэктеста сериализуется в `runs/<run_id>/` (см. FR-6.4) и может быть загружен для повторного анализа без пересчёта.
- **FR-3.6** Бэктест детерминирован: одинаковые вход + конфиг + seed → побитово одинаковый результат.

### FR-4. Метрики и валидация

- **FR-4.1** Рассчитываются метрики из раздела 9.1.
- **FR-4.2** Реализован Walk-Forward Analysis с настраиваемыми окнами (anchored и rolling).
- **FR-4.3** Реализована оптимизация параметров: grid search и `optuna` (TPE), с целевой функцией по выбору (Sharpe, Calmar, custom).
- **FR-4.4** Реализован Monte Carlo: bootstrap перестановка порядка сделок (≥1000 итераций) с доверительными интервалами для MaxDD и итоговой доходности.
- **FR-4.5** Реализован анализ чувствительности параметров (heatmap по двум ключевым параметрам).

### FR-5. Визуализация («удобные графики»)

- **FR-5.1** Streamlit-дашборд, запускаемый одной командой, со страницами:
  1. **Overview** — сводка по последнему/выбранному прогону: карточки метрик, equity curve, drawdown.
  2. **Trades** — таблица сделок с фильтрами (символ, направление, период, результат), сортировкой и экспортом в CSV.
  3. **Chart** — свечной график выбранного символа с наложением индикаторов и **маркерами входов/выходов** (▲ long entry, ▼ short entry, ✕ exit), подсветкой зон удержания позиции, tooltip с деталями сделки.
  4. **Analytics** — распределение PnL и R, месячная/годовая доходность (heatmap), MAE/MFE-диаграммы, кривая по символам, статистика по времени суток/дню недели.
  5. **Walk-Forward** — IS vs OOS сравнение, стабильность параметров во времени, Monte Carlo веер.
  6. **Live** — текущее состояние бота: открытые сигналы, последние сообщения, статус подключения, uptime.
- **FR-5.2** Все графики интерактивные (Plotly): zoom, pan, hover, переключение серий, кроссхейр.
- **FR-5.3** Экспорт самодостаточного HTML-отчёта (`report.html`) одной командой — открывается в браузере без запуска сервера.
- **FR-5.4** Экспорт ключевых графиков в PNG (`kaleido`) для отправки в Telegram.
- **FR-5.5** Возможность выбрать любой прошлый прогон из списка `runs/` и сравнить два прогона бок о бок.

### FR-6. Live-режим

- **FR-6.1** Асинхронный цикл: ожидание закрытия свечи → догрузка последнего бара → пересчёт индикаторов → запрос сигнала у стратегии → сохранение → отправка уведомления.
- **FR-6.2** Режимы: `paper` (виртуальный счёт, ведёт учёт позиций и PnL) и `signal-only` (только уведомления). Режим `live` (реальные ордера) — не реализуется, но интерфейс предусмотрен.
- **FR-6.3** Состояние (открытые позиции, история сигналов, последний обработанный бар) персистится в SQLite. После перезапуска бот восстанавливает состояние и **не дублирует** уже отправленные сигналы (идемпотентность по ключу `symbol+timeframe+bar_ts+signal_type`).
- **FR-6.4** Каждый прогон бэктеста/оптимизации получает `run_id` формата `YYYYMMDD-HHMMSS-<short_hash_конфига>`.
- **FR-6.5** Отслеживание уже открытых (виртуальных) позиций: бот шлёт уведомления не только о входе, но и о срабатывании стопа/тейка/сигнала на выход.

### FR-7. Telegram

- **FR-7.1** Отправка форматированного сообщения при каждом сигнале входа (раздел 11.2).
- **FR-7.2** Отправка сообщения при выходе из позиции с итогом сделки.
- **FR-7.3** Ежедневный сводный отчёт в заданное время (настраивается).
- **FR-7.4** Уведомления об ошибках и о старте/остановке бота.
- **FR-7.5** Команды бота (раздел 11.3).
- **FR-7.6** Доступ ограничен whitelist'ом `chat_id` из конфига. Сообщения от посторонних игнорируются и логируются.
- **FR-7.7** Устойчивость: ретраи с экспоненциальной задержкой, соблюдение rate-limit Telegram, очередь неотправленных сообщений с досылкой после восстановления связи. **Падение Telegram не должно останавливать торговый цикл.**

## 6. Архитектура

### 6.1 Слоистая схема

```
┌──────────────────────────────────────────────────────────┐
│  Интерфейсы:  CLI (typer) │ Streamlit Dashboard │ Telegram │
└───────────────┬──────────────────┬───────────────┬────────┘
                │                  │               │
┌───────────────▼──────────────────▼───────────────▼────────┐
│  Приложение: BacktestRunner │ LiveRunner │ Optimizer │ WFA │
└───────────────┬───────────────────────────────────────────┘
                │
┌───────────────▼───────────────────────────────────────────┐
│  Домен: Strategy │ Indicators │ RiskManager │ Portfolio    │
│         Signal / Position / Trade (модели)                 │
└───────────────┬───────────────────────────────────────────┘
                │
┌───────────────▼───────────────────────────────────────────┐
│  Инфраструктура: DataFeed(ccxt) │ ParquetCache │ SQLite    │
│                  Notifier(Telegram) │ Logger │ Config      │
└────────────────────────────────────────────────────────────┘
```

Ключевой принцип: **домен ничего не знает об инфраструктуре**. `Strategy` получает на вход `DataFrame` и возвращает `Signal | None` — она не ходит в сеть, не пишет в БД и не шлёт сообщения. Это делает её тривиально тестируемой и гарантирует, что бэктест и live используют **один и тот же код стратегии**.

## 7. Спецификация стратегии

### 7.1 Выбор и обоснование

Реализуется стратегия **«Donchian Trend Breakout with ATR risk management»** (рабочее имя `donchian_trend`) — трендследящий пробойный подход в духе Turtle Trading, адаптированный под крипторынок.

Обоснование выбора:
- **Симметрична** — одинаково работает в лонг и в шорт, что прямо требуется заказчиком.
- **Малое число параметров** (6 основных) → низкий риск переоптимизации, что критично при обязательной walk-forward валидации.
- **Правила однозначны и не зависят от внутрибарной динамики** → бэктест честен и воспроизводим.
- Трендследящие пробойные системы имеют длительную опубликованную историю работоспособности на трендовых рынках, к которым относится крипто.

Стратегия — эталонная реализация интерфейса `Strategy`. Добавление альтернативных стратегий в будущем не требует изменений в движке.

### 7.2 Индикаторы и формулы

Все индикаторы считаются на **закрытых** барах. Обозначения: `H`, `L`, `C` — high/low/close текущего бара, индекс `t`.

**EMA(n)**
```
α = 2 / (n + 1)
EMA_t = α · C_t + (1 − α) · EMA_{t−1}
EMA_0 = SMA(C, n) на первых n барах
```

**True Range и ATR(n)** (сглаживание Уайлдера, RMA)
```
TR_t  = max(H_t − L_t, |H_t − C_{t−1}|, |L_t − C_{t−1}|)
ATR_t = ((n − 1) · ATR_{t−1} + TR_t) / n
```

**Donchian Channel(n)** — рассчитывается **со сдвигом на 1 бар**, чтобы текущий бар не участвовал в собственном канале:
```
DC_upper_t = max(H_{t−n} … H_{t−1})
DC_lower_t = min(L_{t−n} … L_{t−1})
DC_mid_t   = (DC_upper_t + DC_lower_t) / 2
```

**ADX(n)** (классический Уайлдер)
```
+DM_t = (H_t − H_{t−1}) if (H_t − H_{t−1}) > (L_{t−1} − L_t) and > 0 else 0
−DM_t = (L_{t−1} − L_t) if (L_{t−1} − L_t) > (H_t − H_{t−1}) and > 0 else 0
+DI_t = 100 · RMA(+DM, n) / ATR_t
−DI_t = 100 · RMA(−DM, n) / ATR_t
DX_t  = 100 · |+DI_t − −DI_t| / (+DI_t + −DI_t)
ADX_t = RMA(DX, n)
```

### 7.3 Параметры по умолчанию

Файл `configs/strategy_donchian_trend.yaml`:

```yaml
strategy:
  name: donchian_trend
  params:
    entry_channel: 20        # период канала для входа
    exit_channel: 10         # период канала для выхода по развороту
    trend_fast: 50           # быстрая EMA для определения режима
    trend_slow: 200          # медленная EMA для определения режима
    atr_period: 14
    adx_period: 14
    adx_min: 20.0            # минимальная сила тренда для входа
    atr_stop_mult: 2.5       # дистанция стопа в ATR
    atr_trail_mult: 3.0      # дистанция трейлинг-стопа (chandelier) в ATR
    breakeven_at_r: 1.0      # перевод стопа в БУ при достижении +1R
    take_profit_r: [2.0]     # частичная фиксация: 50% позиции на +2R
    take_profit_fraction: 0.5
    min_atr_pct: 0.005       # фильтр: ATR/Close должен быть ≥ 0.5% (не входим в мёртвый рынок)
    max_atr_pct: 0.12        # фильтр: ATR/Close ≤ 12% (не входим в экстремальную волатильность)
    cooldown_bars: 3         # запрет на повторный вход после выхода
```

### 7.4 Определение рыночного режима

```
regime_t = UP    если EMA50_t > EMA200_t  И  C_t > EMA200_t
regime_t = DOWN  если EMA50_t < EMA200_t  И  C_t < EMA200_t
regime_t = FLAT  иначе   → входы запрещены
```

### 7.5 Правила входа

**LONG** — все условия одновременно на закрытии бара `t`:
1. `regime_t == UP`
2. `C_t > DC_upper_t` (пробой верхней границы канала за предыдущие 20 баров)
3. `ADX_t >= adx_min`
4. `min_atr_pct <= ATR_t / C_t <= max_atr_pct`
5. Позиции по инструменту нет, и прошло `>= cooldown_bars` с момента последнего выхода
6. Не превышены портфельные лимиты (раздел 7.9)

**SHORT** — зеркально:
1. `regime_t == DOWN`
2. `C_t < DC_lower_t`
3. `ADX_t >= adx_min`
4. Тот же фильтр волатильности
5. Те же ограничения по позиции и cooldown

### 7.6 Расчёт стопа, тейков и размера позиции

```
LONG:
  entry     = цена открытия бара t+1 (см. раздел 8.2)
  stop_loss = entry − atr_stop_mult · ATR_t
  R         = entry − stop_loss
  TP1       = entry + 2.0 · R     (закрывается 50% позиции)

SHORT:
  stop_loss = entry + atr_stop_mult · ATR_t
  R         = stop_loss − entry
  TP1       = entry − 2.0 · R

Размер позиции:
  risk_amount = equity · risk_per_trade_pct          # по умолчанию 1%
  size        = risk_amount / R                       # в базовой валюте
  notional    = size · entry
  size        = min(size, max_notional_pct · equity / entry)   # кэп по плечу
  size        = округление вниз до шага лота инструмента
```

### 7.7 Правила выхода

Позиция закрывается по первому из наступивших событий:

| Приоритет | Событие | Действие |
|---|---|---|
| 1 | Цена коснулась `stop_loss` (внутри бара по `L`/`H`) | Полный выход по цене стопа + slippage |
| 2 | Цена коснулась `TP1` | Частичный выход (50%), остаток переводится на трейлинг |
| 3 | Достигнут `+1R` (`breakeven_at_r`) | Стоп переносится в безубыток (entry + комиссии) |
| 4 | Активен трейлинг: `chandelier_long = max(H за время в позиции) − atr_trail_mult · ATR` | Стоп подтягивается, **никогда не двигается против позиции** |
| 5 | `C_t < DC_lower(exit_channel)_t` для лонга / `C_t > DC_upper(exit_channel)_t` для шорта | Полный выход по цене открытия следующего бара |
| 6 | Смена режима на противоположный | Полный выход по цене открытия следующего бара |

**Разрешение конфликта стоп/тейк внутри одного бара:** если бар одновременно задевает и стоп, и тейк, консервативно считается, что **первым сработал стоп**. Это обязательное требование — оно исключает завышение результатов бэктеста.

### 7.8 Разворот позиции

Прямой переворот (reverse) запрещён. Сначала выход, затем — не ранее чем через `cooldown_bars` — возможен вход в противоположную сторону.

### 7.9 Риск-менеджмент (портфельный уровень)

```yaml
risk:
  risk_per_trade_pct: 0.01        # 1% капитала на сделку
  max_concurrent_positions: 3
  max_positions_per_side: 3
  max_notional_pct: 0.35          # ≤35% капитала в одной позиции
  max_portfolio_risk_pct: 0.03    # суммарный риск открытых позиций ≤3%
  daily_loss_limit_pct: 0.05      # при −5% за сутки: стоп новых входов до след. суток
  max_drawdown_stop_pct: 0.25     # при −25% от пика: полная остановка + алерт в Telegram
```

При отклонении сигнала риск-менеджером факт отклонения **логируется с причиной** и (опционально, по флагу конфига) отправляется в Telegram как информационное сообщение.

## 8. Спецификация бэктест-движка

### 8.1 Модель издержек

```yaml
costs:
  taker_fee: 0.0005          # 0.05% — вход по маркету
  maker_fee: 0.0002
  slippage_model: atr        # варианты: fixed_bps | atr | percent
  slippage_bps: 5            # для fixed_bps
  slippage_atr_mult: 0.05    # для atr: проскальзывание = 0.05 · ATR
  funding_rate_8h: 0.0001    # 0.01% за 8 часов удержания
  apply_funding: true
```

Комиссия берётся при входе и при каждом (в т.ч. частичном) выходе. Funding начисляется каждые 8 часов удержания позиции пропорционально нотионалу, со знаком в зависимости от направления.

### 8.2 Порядок обработки бара (критично для отсутствия look-ahead)

Для каждого бара `t` движок выполняет строго следующую последовательность:

1. **Открытие бара `t`:** исполняются ордера, поставленные в очередь на предыдущем баре (`t−1`), по цене `open_t` ± slippage. Именно здесь происходит фактический вход/выход по сигналу.
2. **Внутри бара `t`:** проверка срабатывания стопов и тейков открытых позиций по `high_t`/`low_t`. При конфликте — приоритет у стопа (раздел 7.7).
3. **Начисление funding**, если пройдена 8-часовая граница.
4. **Закрытие бара `t`:** индикаторы обновляются значениями бара `t`; вызывается `strategy.on_bar()`; возвращённый `Signal` **ставится в очередь на исполнение на открытии бара `t+1`**.
5. **Переоценка equity** по `close_t` (mark-to-market), запись точки equity curve.

Правило, которое должно быть покрыто отдельным тестом: **сигнал, сформированный на закрытии бара `t`, физически не может быть исполнен по цене бара `t`.**

### 8.3 Учёт капитала

- Начальный капитал: `10 000 USDT` (конфигурируемо).
- Единая валюта учёта — USDT.
- Реинвестирование прибыли включено (размер позиции считается от текущего equity).
- Плечо не моделируется явно; ограничение задаётся через `max_notional_pct`.
- Фиксируются и `balance` (реализованный), и `equity` (с учётом открытых позиций).

## 9. Метрики и валидация

### 9.1 Обязательный набор метрик

**Доходность**
- Total Return, %
- CAGR, %
- Buy & Hold Return (бенчмарк по каждому символу и по портфелю)
- Alpha относительно Buy & Hold
- Месячная и годовая доходность (таблица + heatmap)

**Риск**
- Max Drawdown, % и в абсолюте
- Длительность максимальной просадки (дни) и время восстановления
- Средняя просадка
- Annualized Volatility
- Value at Risk (95%), Conditional VaR (95%)
- Ulcer Index

**Соотношение риск/доходность**
- Sharpe Ratio (безрисковая ставка конфигурируема, по умолчанию 0)
- Sortino Ratio
- Calmar Ratio
- Omega Ratio

**Торговая статистика**
- Число сделок, отдельно long / short
- Win Rate, %
- Profit Factor
- Expectancy в R и в USDT
- Средний выигрыш / средний проигрыш, в R
- Максимальная серия выигрышей / проигрышей
- Среднее время в позиции (баров и часов)
- Exposure Time, % (доля времени в рынке)
- Распределение по `exit_reason`
- MAE / MFE — среднее и диаграмма рассеяния

**Издержки**
- Суммарные комиссии, funding, оценка проскальзывания
- Доля издержек в валовой прибыли

Требование: все формулы метрик покрыты юнит-тестами на синтетических данных с заранее известным ответом.

### 9.2 Walk-Forward Analysis

- Режимы: `rolling` (скользящее окно) и `anchored` (растущее окно).
- Значения по умолчанию: IS = 18 месяцев, OOS = 6 месяцев, шаг = 6 месяцев.
- В каждом окне: оптимизация параметров на IS → применение лучших параметров к OOS без изменений → склейка OOS-отрезков в единую «честную» equity curve.
- Отчёт: таблица окон (период, лучшие параметры, IS-метрики, OOS-метрики), **WFE (Walk-Forward Efficiency) = OOS_return / IS_return**, график стабильности параметров во времени.
- Критерий здоровья стратегии: WFE ≥ 0.5 и положительный OOS-результат в ≥ 60% окон. Если критерий не выполнен — это фиксируется в отчёте честно, без подгонки.

### 9.3 Оптимизация

- `grid` — полный перебор по сетке из конфига.
- `optuna` — TPE-сэмплер, число трайлов настраивается, поддержка pruning.
- Целевые функции на выбор: `sharpe`, `calmar`, `profit_factor`, `custom` (`Calmar × log(1 + n_trades)` — штрафует стратегии с малой статистикой).
- Защита от переоптимизации: минимальное число сделок (по умолчанию 30), иначе комбинация отбраковывается.
- Результат — таблица всех комбинаций + heatmap чувствительности по двум выбранным параметрам. **Выбирать нужно не пиковую комбинацию, а центр устойчивого плато** — это фиксируется в `docs/strategy.md`.

### 9.4 Monte Carlo

- Bootstrap-перестановка порядка сделок, ≥1000 итераций.
- Выход: распределение итогового капитала и MaxDD, перцентили 5/25/50/75/95, вероятность просадки > 20%, вероятность разорения.
- График: «веер» equity-кривых с доверительными интервалами.

### 11.4 Надёжность

- Ретраи: `tenacity`, экспоненциальный backoff, до 5 попыток.
- Обработка `RetryAfter` от Telegram с ожиданием указанного времени.
- Не более 20 сообщений в минуту на чат; при превышении сообщения буферизуются.

## 13. Хранение данных

### 13.1 Parquet-кэш OHLCV

Путь: `data/ohlcv/{exchange}/{symbol_sanitized}/{timeframe}.parquet`
Колонки: `ts` (datetime64[ns, UTC], время открытия бара, индекс), `open`, `high`, `low`, `close`, `volume` (float64), `is_gap` (bool).
Догрузка: читается последний `ts`, запрашиваются данные начиная с него, склейка с дедупликацией по `ts`.

### 13.2 SQLite (состояние live-режима)

Таблицы:

- **`signals`** — `id`, `signal_uid` (unique), `symbol`, `timeframe`, `bar_ts`, `side`, `signal_type`, `price`, `stop_loss`, `take_profits` (JSON), `size`, `risk_pct`, `reason`, `indicators` (JSON), `created_at`, `notified_at`, `status`
- **`positions`** — `id`, `symbol`, `side`, `entry_ts`, `entry_price`, `size`, `current_stop`, `initial_stop`, `tp_levels` (JSON), `realized_pnl`, `status` (OPEN/CLOSED), `signal_uid`
- **`trades`** — закрытые сделки, схема из раздела 8.4
- **`equity_snapshots`** — `ts`, `balance`, `equity`, `open_positions_count`, `drawdown_pct`
- **`bot_state`** — `key`, `value` (JSON): `last_processed_bar`, `paused`, `started_at`
- **`notification_queue`** — `id`, `payload` (JSON), `attempts`, `last_error`, `created_at`, `sent_at`

Уникальный индекс на `signals.signal_uid` — техническая гарантия отсутствия дублирующих уведомлений.
Миграции — через `alembic` (или через версионированные SQL-скрипты, если alembic избыточен).

## 14. Логирование и обработка ошибок

- `loguru`: консоль (цветной human-readable) + файл (JSON-строки), ротация 10 МБ, retention 14 дней.
- Контекст в каждой записи: `run_id`, `symbol`, `bar_ts`, модуль.
- Уровни: `DEBUG` — значения индикаторов; `INFO` — сигналы, входы/выходы, старт/стоп; `WARNING` — пропуски данных, отклонённые сигналы, ретраи; `ERROR` — сбои API, исключения; `CRITICAL` — остановка бота.

**Классификация ошибок и поведение:**

| Класс | Пример | Реакция |
|---|---|---|
| Transient network | Timeout, 502 от биржи | Ретрай (5 попыток, exponential backoff), затем WARNING |
| Rate limit | 429 | Ожидание по заголовку Retry-After |
| Data integrity | Пропуск баров, NaN | WARNING, пропуск бара, алерт в Telegram при >`max_gap_bars` |
| Config error | Неверный YAML | Падение при старте с понятным сообщением |
| Strategy error | Исключение в `on_bar` | ERROR, бар пропускается, торговый цикл продолжается, алерт в Telegram |
| Notification error | Telegram недоступен | Сообщение в очередь, цикл продолжается |
| Critical | Достигнут max drawdown stop | Остановка новых входов, CRITICAL-алерт |

Graceful shutdown по `SIGINT`/`SIGTERM`: сохранение состояния, досылка очереди уведомлений, корректное закрытие соединений.

## 15. Тестирование

### 15.1 Юнит-тесты (обязательный минимум)

- **Индикаторы:** сверка с заранее рассчитанными эталонными значениями на фикстуре из 200 баров; проверка поведения на warmup-периоде и на константном ряде.
- **Donchian:** тест, доказывающий сдвиг на 1 бар (текущий бар не входит в собственный канал).
- **Стратегия:** синтетические сценарии — чистый восходящий тренд с пробоем (ожидается LONG), нисходящий (SHORT), боковик (нет сигналов), ADX ниже порога (нет сигнала), ATR вне диапазона (нет сигнала), cooldown (нет повторного входа).
- **Sizing:** размер позиции при заданных equity/риске/ATR совпадает с расчётом вручную; корректное округление до шага лота; срабатывание кэпа `max_notional_pct`.
- **Broker:** корректность комиссий, slippage, funding; частичное закрытие; конфликт стоп/тейк в одном баре → выбран стоп.
- **Движок (анти-look-ahead):** тест, который подаёт данные, где будущий бар содержит экстремальное движение, и проверяет, что сигнал бара `t` исполнен по `open_{t+1}`, а не по `close_t`.
- **Метрики:** известная последовательность доходностей → точные ожидаемые Sharpe/MaxDD/Profit Factor.
- **Детерминизм:** два запуска с одним конфигом дают идентичные `trades.parquet` (сравнение хэшей).
- **Идемпотентность уведомлений:** повторная обработка того же бара не создаёт второго сообщения.
- **Формат сообщений:** снапшот-тест текста Telegram-сообщения.

### 15.2 Интеграционные тесты (маркер `integration`, вне CI по умолчанию)

- Реальная загрузка 100 баров с Binance через ccxt.
- Полный бэктест на реальных данных за 1 год: завершается без исключений, метрики в разумных пределах.
- Отправка тестового сообщения в Telegram (только при наличии токена в env).

### 15.3 Приёмочный сценарий (smoke, документируется в README)

```bash
make install
make download          # загрузка данных
make backtest          # бэктест
make report            # генерация report.html
make dashboard         # дашборд открывается, графики отрисованы
make telegram-test     # сообщение доставлено
make bot               # paper-режим стартует и логирует ожидание следующего бара
```

## 19. Правила работы с git

### 19.1 Обязательное требование по авторству коммитов

**В коммитах категорически запрещено указывать Cursor, AI-ассистента или любые автоматические трейлеры соавторства.**

Конкретно, в сообщении коммита **не должно быть**:
- строк `Co-authored-by: Cursor ...` / `Co-Authored-By: Claude ...` / любых `Co-authored-by`, ссылающихся на AI-инструмент;
- упоминаний `Generated with Cursor`, `Made with AI`, эмодзи-подписей вроде `🤖`;
- любых иных трейлеров, указывающих на автоматическую генерацию.

Автор и коммиттер — только человек-владелец репозитория.

Проверка перед каждым push:

```bash
git log --format='%an <%ae>%n%B' -20 | grep -iE 'cursor|co-authored|claude|generated with|🤖' && echo "НАЙДЕНЫ ЗАПРЕЩЁННЫЕ УПОМИНАНИЯ" || echo "OK"
```

Команда должна печатать `OK`.

### 19.2 Формат сообщений (Conventional Commits)

```
<type>(<scope>): <краткое описание в повелительном наклонении, англ., ≤72 символов>

<необязательное тело: что и зачем, а не как>
```

Типы: `feat`, `fix`, `refactor`, `test`, `docs`, `chore`, `perf`, `ci`.

### 19.3 Процесс

1. Реализовать этап из раздела 17.
2. Прогнать `make lint typecheck test`.
3. `git add -A && git commit -m "<сообщение из этапа>"`.
4. Проверить историю командой из 19.1.
5. `git push origin main`.
6. Только после этого переходить к следующему этапу.

Ветка по умолчанию — `main`. Force-push в `main` запрещён.

## 20. Риски и ограничения

| Риск | Влияние | Митигация |
|---|---|---|
| Переоптимизация параметров | Стратегия хорошо выглядит на истории и не работает в будущем | Обязательный walk-forward, малое число параметров, выбор плато вместо пика, Monte Carlo |
| Look-ahead bias | Ложно завышенные результаты | Жёсткий порядок обработки бара (8.2) + обязательный тест в CI |
| Survivorship bias | Тестирование только на «выживших» монетах | Явное указание ограничения в отчёте; фиксированный список символов с датами листинга |
| Недооценка издержек | Реальный результат хуже бэктеста | Консервативные комиссии, ATR-модель проскальзывания, учёт funding, анализ доли издержек |
| Изменение API биржи | Остановка загрузки данных | Абстракция `DataFeed`, ретраи, алерты в Telegram |
| Разрыв связи в live-режиме | Пропуск сигнала | Догрузка пропущенных баров при восстановлении, обработка «задним числом» с пометкой delayed |
| Утечка токена Telegram | Компрометация бота | Секреты только в env, `detect-private-key` в pre-commit, `.env` в `.gitignore` |
| Расхождение логики бэктеста и live | Live торгует иначе, чем показал бэктест | Единый класс `Strategy` для обоих режимов; тест, сравнивающий сигналы бэктеста и live-движка на одинаковых данных |
| Слабый рыночный режим (боковик) | Серия убытков | Фильтры ADX и ATR, дневной лимит убытка, max drawdown stop |
